# Notes SQLite storage and S3 synchronization

Notes are local-first records in `<userData>/notes.sqlite3`. The database contains Note content, metadata, deletion records, and hierarchy/sibling order. The main process owns SQLite and all S3 credentials. The renderer continues to use the existing validated Notes IPC. Tree expansion, tabs, fonts, theme, credentials, and other device preferences are not in the synchronized database. Images, attachments, and shared HTML remain separate S3 objects.

## Migration

The first launch recovers any interrupted legacy workspace apply, reads `notes-v4` and `notes-tree.json`, builds and checks a temporary database, and atomically installs it. Existing databases are validated and never replaced with an empty database after an error. Migration retains the original local files. The packaged and development profiles remain separate; migration reads only the active profile.

Local migration works offline. On the first successful S3 connection, the app checks `service-manager-sync-v5/notes/database.sqlite3.enc`. Only a confirmed missing database permits legacy v4 import. If the local Notes workspace still matches its last committed legacy manifest, the latest legacy cloud Notes are imported, including tree and deletions. If local Notes differ from that base, the local whole workspace wins and the immutable legacy cloud objects remain available. With no known legacy base, edits made since local database initialization count as local changes. This first migration does not merge two divergent workspaces; both sources remain recoverable.

Once the new cloud database exists, new clients use it and do not import later changes from old v4 clients. Upgrade all editing devices together. Running an old version after migration creates a separate legacy history; downgrade does not automatically include subsequent SQLite edits. Existing Conflict Notes are preserved as ordinary historical Notes.

## Synchronization rules

- Saves commit locally through SQLite transactions with WAL and full synchronous durability. Cloud publication waits for 30 seconds without a local save; continuous editing is capped at five minutes since the previous successful sync (or first pending save). A single upload runs at a time; edits during upload remain pending for the next batch. Startup and manual sync can publish immediately. One-minute background checks reconcile Hosts/Proxy and inspect Notes without uploading the database or clearing its pending state. While Notes is open, immediate and five-second checks detect remote changes.
- Leaving Notes flushes local drafts and requests an upload only if the database has pending changes; it never grants permission to pull remote updates and respects retry backoff. Failures retry after 30 seconds, one minute, two, four, eight, then at most fifteen minutes. Typing cannot bypass this retry floor. Remote-update/divergence locks retain the existing protections. Manual sync and an explicit quit-sync can retry immediately.
- Notes displays local save and cloud sync status separately. Normal quit and update installation always require confirmation, with Cancel selected by default. Drafts are flushed/frozen first. With S3 configured, the dialog shows the Notes state (last verified synced, pending upload, syncing, offline, remote update, diverged, or unverified), even when nothing is pending. Without S3 it shows a simple quit confirmation. Pending uploads can be synchronized before quitting; failed sync offers retry or local-only quit. This happens before the existing eight-second runtime-cleanup deadline. System termination signals retain the bounded emergency shutdown path. Closing a macOS window without quitting the app retains the existing local-flush behavior; background uploads continue while the process runs.
- The window-close shortcut closes the selected Notes tab, including the last one. With no open tabs, Notes shows an empty workspace with a New note action and continues consuming the shortcut so it cannot accidentally close the window. Closed Notes remain in the sidebar, and background reloads do not reopen a deliberately empty tab set. Unsaved-draft close confirmation remains in place.
- No S3 configuration means no remote checks, warnings, or editing restrictions. With S3 configured, Notes remains read-only until the initial check finishes. A remote-only update locks editing until the user clicks Sync. An unreachable/unverifiable remote locks editing and offers Edit anyway with a divergence warning. Offline consent lasts only until a successful check (or app restart); a later outage requires consent again. Known remote updates or divergence never offer an offline bypass.
- Unchanged cloud checks use a conditional GET with the last confirmed ETag. If both cloud and local records are unchanged, no database body is downloaded or local backup file created. Changed uploads fetch the previous cloud bytes for recovery before replacement.
- A consistent SQLite backup produces a closed, standalone database containing committed WAL changes. The live file and its WAL/SHM files are never copied independently to S3.
- The database is encrypted with AES-256-GCM and a domain-separated HKDF key derived from the existing Sync Encryption Key. The binary envelope authenticates its version, key identity, length, salt, IV, and content. The unencrypted snapshot limit is 128 MiB. Large or corrupt transfers fail without replacing local data.
- Local changes are detected by a canonical fingerprint of Notes, tombstones, and tree, relative to a durable device-local checkpoint. SQLite page bytes, file timestamps, and device wall clocks do not decide precedence.
- Compare both content hashes with the last synchronized hash. Local-only changes may upload automatically. Remote-only changes require manual Sync to download and apply. If both changed to different contents, both upload and download are blocked, including manual Sync, and both copies remain intact. This applies even if different Notes were edited. Identical contents are not a conflict. A previously synchronized remote database disappearing also blocks synchronization.
- Each upload first reads and backs up the cloud version, then uses its ETag as a write condition. On a competing upload, the app re-reads and reclassifies; divergence stops the retry without overwriting either database. Equivalent-content races can retry up to four attempts. A new object uses `If-None-Match: *`. This requires S3/MinIO support for conditional object writes.
- An upload acknowledges only the captured fingerprint. Edits made during upload remain pending. A pull freezes and flushes editors, then checks the local fingerprint within the same mutation queue before applying. Late local edits trigger a retry; they are not silently replaced by the earlier download.
- The incoming database is opened read-only, with trusted schema disabled, and checked for supported schema, integrity, bounded rows, and valid application data. Validated records are applied into the existing local database through the durable workspace coordinator. Local SQLite connections are not replaced underneath active operations.
- Durable apply and upload intentions recover interrupted acknowledgements. A matching uploaded database is acknowledged after restart without republishing. If an interrupted upload has an unknown outcome and the cloud has subsequently changed, synchronization is conservatively blocked instead of guessing which version to replace.
- Main-process mutation guards protect create/update/delete/move/recovery/import operations as well as the UI. When an editable workspace must be locked, editors are frozen and flushed first, then hashes are reclassified before publishing the lock, preserving late drafts. The guard does not expose S3 credentials or raw database access to the renderer.

Hosts and Proxy retain the v4 manifest/head merge behavior. Routine settings publication carries forward the latest legacy Notes references without reading or modifying those objects. A Notes remote-update/divergence lock does not block settings reconciliation. Key rotation re-encrypts retained legacy Notes and the database; the previous protected key is retired only after both sync paths succeed. Failed remote verification requires explicit offline-editing consent.

## Recovery

`<userData>/notes-database-recovery` contains private encrypted standalone database backups. `before-pull-*` is the local workspace before a cloud replacement; `before-push-*` is the cloud database about to be overwritten by this device. The newest 20 routine snapshots are retained. `migration-*` backups are retained separately, along with the original local legacy files and immutable S3 v4 history. Recovery files never upload automatically.

Backups use the same binary format as the cloud database. To recover, retain a copy of the current profile and stop all app instances, decrypt a chosen backup with the Sync Encryption Key used when it was created using `decryptNotesDatabase`, and validate it using `SqliteNotesStore.decodeSnapshot` before restoring. Retain old keys if old backups must remain recoverable after key rotation. Do not replace a live SQLite file or leave unrelated WAL/SHM files beside a restored database. Recovery is a developer-assisted operation in this release; there is no new recovery browser in the UI.

## Development and verification

Install dependencies manually with `pnpm install`. `better-sqlite3` is a native dependency; the Node ABI in the shell can differ from Electron's ABI. `pnpm dev`, `pnpm start`, and `pnpm test` prepare it for Electron. Tests run with Electron's Node runtime via `scripts/run-electron-tests.cjs`. After preparation, pass test filenames to that script for focused verification. Packaging rebuilds native modules for the target OS and architecture. Type checking and renderer compilation remain part of `pnpm build`.

Regression coverage includes local migration and damaged input, WAL snapshot consistency, whole-workspace precedence, conditional publication, late editing, pending work across restarts, legacy v4 preservation, encryption rotation, cancellation, and offline failures. Cross-platform packages must still be exercised on their target platforms before release.
